UUID v4 vs v7 for database keys: a workload-based choice

Randomness and temporal locality are useful properties, but neither version is universally best.

DevTools Hub Editorial Team8 min readNovember 8, 2026

UUIDs let independently operating clients and services create identifiers without coordinating through one central counter. Database key design introduces a second question: how will those identifiers behave in indexes and reveal information? UUID version 4 and version 7 encode different trade-offs. Version 4 is broadly random. Version 7 begins with a timestamp and can sort approximately by creation time. The better choice depends on workload, privacy, database implementation, interoperability, and whether ordering has domain meaning.

What a database key needs to do

A primary key uniquely identifies a row within its table and supports relationships and lookup. It should be stable, representable in every system that uses it, and managed consistently across writes and replication. Some teams also want keys to be generated before a database insert, exposed safely in an API, or ordered approximately by creation. These are distinct requirements. A key’s format does not replace authorization, and a random-looking identifier does not make an object private if the service fails to check access.

UUIDs contain 128 bits and are commonly stored as a native 16-byte binary value or rendered in a 36-character hyphenated string. The choice of storage representation can affect index size and CPU conversions. Before replacing integer keys, measure the actual database and client libraries, check constraints and ORM support, and identify foreign keys and external references. A UUID changes more than the primary-key column if it appears in URLs, messages, logs, caches, or analytics.

UUID v4: independent random values

Version 4 reserves bits for the version and variant and fills the remaining 122 bits with random values. With a suitable cryptographic random source, the probability of collision remains extremely small at ordinary scales. V4 does not encode creation time, so sorting identifiers has no useful temporal meaning and an ID does not disclose its approximate issue time. That can be desirable when records are publicly addressable, though it is not a substitute for an authorization check.

The cost of random distribution can matter in an index. In a B-tree, inserts into unrelated key ranges can produce page splits and reduce locality compared with a steadily increasing key. This is not a fixed performance penalty across every database, index, or workload. Cache sizes, fill factors, batching, page layout, concurrent writes, storage engine, and actual query patterns all affect the result. Benchmark before treating the theoretical difference as a production conclusion.

UUID v7: timestamp-leading values

Version 7, standardized in RFC 9562, places a 48-bit Unix timestamp in milliseconds at the start of the identifier and uses version/variant bits plus random data in the remaining positions. Canonical string ordering is broadly time-ordered, which may improve index locality for rows inserted in time order. It also makes an approximate generation time visible to anyone who can inspect the key. If that timing is sensitive, consider where the identifier appears and whether another identifier or access layer is more appropriate.

V7 is not a globally synchronized sequence. Several IDs can be created in the same millisecond, and random portions provide separation. Generator implementations may use monotonic counters or other strategies, but those are not interchangeable assumptions. Clock skew, clock adjustments, replicated generation, and events arriving late all mean that lexical order is not guaranteed to match business event order. If a strict event sequence matters, store an explicit sequence or event time with documented semantics.

Compare the trade-offs directly

  • Index locality: V7’s timestamp prefix can cluster nearby inserts; V4 distributes them. Test with your storage engine and write pattern.
  • Time disclosure: V4 hides creation time in its format; V7 reveals approximate millisecond time.
  • Offline generation: Both can be generated without a central counter, subject to each implementation’s entropy and clock behavior.
  • Sort semantics: V7 can support approximate chronological order; neither UUID version guarantees domain-event ordering.
  • Compatibility: Verify the language runtime, database type, library, validator, and downstream integrations understand version 7.

How to evaluate the choice

Start with the problem you are trying to solve. If the existing integer key is compact and works well, changing to a UUID because it is fashionable can create unnecessary costs. If independent write sites need IDs before persistence, UUIDs may simplify the architecture. If random inserts have been measured as a bottleneck, compare UUID v7 with other options under representative load. Include inserts, range scans, replication lag, index size, vacuum or maintenance behavior, and the effect on secondary indexes.

Use a repeatable benchmark rather than a toy test. Generate representative data, use the same schema and indexes, warm or reset the cache consistently, and record both throughput and tail latency. Include concurrent writes and the read queries your product actually uses. Inspect the database’s execution plans and storage metrics. Ensure IDs are generated with the production-grade library and settings; a benchmark using a different UUID generator can produce misleading behavior.

Migration and safety considerations

Changing a primary key in an established system is a distributed data migration. Plan how to backfill values, update foreign keys, dual-read or dual-write during a transition, propagate IDs through messages, and retain old identifiers for integrations. Test rollback and restore procedures. Unique constraints still matter even when collisions are improbable, and the application should handle a conflict safely. Monitor migration load, replication, lock duration, and compatibility with old clients.

UUIDs should not be used as bearer credentials merely because a value looks hard to guess. Check ownership and authorization on every read and mutation. V7 IDs can leak record creation patterns; V4 IDs still appear in logs and may be correlated. Use dedicated, revocable tokens for authentication and use the minimum identifier exposure appropriate for the API.

The UUID generator can help create sample v4 and v7 values for tests. The tool’s output is not a database performance benchmark or substitute for a production library. Read the UUID standard, database documentation, and your application’s data-retention requirements before deciding. Choose based on measured behavior and documented trade-offs rather than a universal rule.

Decision shortcut

Use v4 when random, timestamp-independent IDs suit the system; investigate v7 when time locality is valuable and its metadata disclosure is acceptable.
