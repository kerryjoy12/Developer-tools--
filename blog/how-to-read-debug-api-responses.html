Debugging

How to read and debug API responses methodically

Start with the evidence on the wire, then narrow the problem one layer at a time.

8 min readNovember 8, 2026

An API call is not just a JSON body. It is an HTTP request and response with a method, URL, headers, status code, timing, and possibly a body. When an application reports “the API is broken,” the cause could be routing, authentication, content negotiation, a proxy, a server exception, a schema mismatch, or client parsing. Inspecting these layers in a deliberate order turns a vague failure into a reproducible question.

1. Reproduce one exact request

Record the method, full path, relevant query parameters, request headers, and request body. Include the environment and time of the request, but remove credentials and personal information before sharing. Check whether the failure occurs consistently, only for one account, or only behind a certain network. A minimal repeatable request is more useful than a screenshot of a generic error toast. Prefer a local fixture or sanitized sample when the original payload contains customer data.

Make sure the URL is actually the one you intended. Query strings can contain repeated keys and encoded delimiters; a space or ampersand in a parameter may change the server’s interpretation if it was not escaped correctly. Browser network panels, command-line clients, and SDK logs each present the request differently, so compare the raw method and headers rather than relying on a transformed display.

2. Read the status before the body

The HTTP status gives a useful first classification. A 2xx response indicates the server reports success, but does not prove that the returned data meets your application’s contract. A 3xx may indicate a redirect, authentication gateway, or canonical route. A 4xx often points to the request, permissions, rate limits, or resource state. A 5xx suggests a server-side failure, but a reverse proxy or upstream service can generate it too. Status-code families are clues, not an explanation: read the API’s documented behavior for the exact code.

Also inspect redirects and timing. A request can end at a login page or gateway while the client expects an API response. A timeout does not mean the server did nothing; retrying a non-idempotent operation can create duplicates. Verify whether the operation is safe to repeat and whether the API supports idempotency keys before retrying.

3. Inspect response headers

The Content-Type header indicates how to interpret the response. A 200 response with HTML may be a proxy-generated page, not JSON. Cache headers can explain why a stale response is returned. Authentication challenges, rate-limit headers, request IDs, and server timing can help route the investigation to the right team. Keep headers private when they contain session tokens, cookies, or internal infrastructure details.

Cross-origin browser requests can fail even when the server returned a response, because the browser enforces CORS before exposing it to page code. A failed fetch in the console may therefore differ from a command-line request. Do not solve CORS by disabling browser security in production; configure the server to allow only the correct origins and methods.

4. Parse the body, then validate its meaning

Capture the exact bytes or text body. If the endpoint claims to return JSON, parse it using a real parser; a pretty-printed console object may hide the raw syntax. An invalid JSON error often means the body is an HTML error page, is truncated, or has an encoding issue. A JSON parser can confirm grammar, but the result still needs schema and business validation. Check required fields, types, nullability, enum values, and whether a number exceeds the exact range of the client language.

Do not assume every successful response has a body. Some methods and status codes intentionally return no content. Conversely, an error response can have a structured body with a request identifier or validation details. Let the client handle empty bodies deliberately rather than calling a JSON parser unconditionally. When using an API that returns pagination cursors, next links, or partial results, inspect those fields before concluding that records are missing.

5. Compare the contract and client assumptions

Read the API documentation or OpenAPI description for the endpoint version you called. Confirm required fields, accepted content types, authentication scheme, response envelopes, pagination, and rate limits. Compare a working request with the failing request, changing one variable at a time. If the server’s response changed, identify whether there was a deployment, schema version, or feature-flag change. Contract tests can catch an accidental incompatibility before it reaches production.

Client-side display can also obscure valid data. Check whether the code expects a list but receives an envelope such as {"data":[...]}, interprets a string field as a number, assumes fields are never null, or conflates missing and empty values. Keep transport parsing, domain mapping, and UI formatting as distinct steps so errors can be traced to the right layer.

6. Handle retries, rate limits, and observability

For a 429 response, follow documented rate limits and any Retry-After guidance. Exponential backoff with jitter can reduce synchronized retry storms, but only retry operations that are safe or protected by idempotency. A request ID from the response can correlate with server-side logs; retain it alongside timestamps and sanitized context. Avoid copying full authorization headers or customer payloads into a ticket.

When behavior is intermittent, collect a small set of measurements: latency, response status, route, deployment version, request ID, and a privacy-reviewed error category. Avoid logging secrets or entire request bodies by default. Redaction should happen before persistence, and logs need access controls and retention limits. Client-side tools can help inspect a sanitized response but are not an observability system.

A compact checklist

  1. Reproduce the exact request and remove secrets from any shared example.
  2. Check status, redirects, request ID, and response timing.
  3. Inspect content type and body as raw text before assuming JSON.
  4. Parse syntax, then validate schema and business rules independently.
  5. Compare the request to the endpoint contract and a known-good case.
  6. Handle retries only when safe; capture sanitized evidence for follow-up.

The JSON Formatter can help inspect a sanitized JSON body, and the URL tool can explain query-value escaping. Neither uploads the text to a conversion service. Read the JSON syntax guide when parsing fails, and remember that a locally processed sample can still be sensitive on a shared screen or in clipboard history.

Troubleshoot in layers

Request → status and headers → raw body → parser → schema → application behavior. Preserve evidence while removing secrets.
