encodeURI vs encodeURIComponent: choose by URL component

Both methods escape text, but they preserve different punctuation for different jobs.

DevTools Hub Editorial Team8 min readNovember 8, 2026

JavaScript has two familiar functions for percent-encoding text: encodeURI and encodeURIComponent. Their names look like a small API choice, but the wrong choice can change the structure of a link. The practical rule is simple: use component encoding for one value that will occupy one part of a URL; use full-URL encoding only when you already have a complete address and want to preserve its separators. In application code, URL construction APIs are often better than applying either function to a hand-built string.

URLs contain syntax and data

A URL contains components such as a scheme, host, path, query, and fragment. Punctuation has structural meaning: slashes separate path segments, a question mark starts the query, ampersands separate common query fields, an equals sign separates a field name and value, and a hash introduces a fragment. Those same characters can also appear as ordinary data inside a component. The job of encoding is to distinguish the data occurrence from the structural occurrence by escaping the data character where necessary.

For example, consider the search value tea & coffee. If you append that raw value after ?q=, the ampersand can be interpreted as the start of another parameter. Component encoding converts the value’s ampersand to %26 and the space to %20, preserving the query structure around it. The intended URL becomes ?q=tea%20%26%20coffee, where the delimiter between query fields remains unescaped and the ampersand inside the user’s value does not.

What encodeURIComponent preserves

encodeURIComponent(value) treats its argument as a single component value. It escapes many reserved delimiters, including /, ?, &, =, #, and :, as well as spaces and non-ASCII UTF-8 bytes. This makes it the more appropriate of the two when inserting a user-provided query value, a path segment, or fragment text into a known location. A path segment such as folder/a becomes one segment rather than two.

It is not a general-purpose sanitizer. The result is suitable for a URI component, not automatically safe in HTML, JavaScript source, SQL, a shell command, or an HTTP header. It also does not validate that the value is semantically correct. If an API expects a numeric page number, encoding the text not-a-number does not make it valid input. Validation and output encoding must match the eventual context.

What encodeURI preserves

encodeURI(address) leaves URL syntax characters such as :, /, ?, &, =, and # in place. It is intended for a complete URI whose structure should remain legible while spaces and many non-ASCII characters are escaped. Passing an entire value to it when that value will be embedded inside another query parameter is often wrong: it leaves separators unescaped, allowing the inner URL’s question mark or ampersand to interfere with the outer URL.

Full-address encoding also has subtle boundaries. It does not repair malformed input, normalize a host name, resolve dot segments, or decide whether a reserved character is data or syntax in a specific component. A complete address that contains an unexpected raw delimiter may still have the wrong meaning after encoding. Parse, validate, and build URLs using APIs that understand their components rather than relying on one global transformation.

Prefer structured URL APIs for composition

When creating URLs in browser JavaScript, the URL and URLSearchParams interfaces help separate structure from values. Build a base URL, then set a query parameter through the API:

const url = new URL("https://example.test/search");
url.searchParams.set("q", "tea & coffee");
url.searchParams.append("tag", "hot drinks");
console.log(url.href);

The API serializes the values according to URL and form-query rules. It also avoids common errors such as forgetting a question mark or inserting a second equals sign. In server-side languages, use that ecosystem’s URI builder rather than copying browser behavior blindly. Different encodings—form encoding, URI components, path segments—have distinct rules and may represent spaces differently.

Decoding and the plus sign

decodeURIComponent reverses a URI component, but it throws when percent escapes are malformed or bytes do not form valid UTF-8. In application/x-www-form-urlencoded query strings, a plus sign commonly means a space; in a generic URI component, plus can be a literal plus. This is why a query parser or URLSearchParams is preferable to a universal decode function when the exact query convention matters.

A common debugging trap is decoding the same text twice. The sequence %2526 decodes once to %26, and a second decode turns that into &. Decode each protocol layer exactly once. If a percent-encoded value is already the literal data expected by the next layer, another decoding step can change it into a delimiter and create injection or routing bugs.

Quick decision table

  • One query value: use structured query parameters; otherwise use component encoding.
  • One path segment: encode the segment, not the slash-separated path as one value.
  • Complete known address: use a URL parser/builder; full-URI encoding may help with a preassembled string, but it is not validation.
  • Untrusted URL: parse it, validate allowed scheme/host/path, and avoid using encoding as an allowlist.
  • Already encoded value: identify its layer before changing it; avoid repeated decoding.

DevTools Hub’s URL Encoder & Decoder exposes component and full-URL modes and lets you inspect query key/value pairs. Try values containing spaces, ampersands, Unicode, plus signs, and percent symbols to see why scope matters. For production logic, test the exact URLs your application emits and consumes, including duplicate parameters, fragments, empty values, and malformed input.

Rule of thumb

Keep URL structure as structure. Encode only the data value that will occupy a specific component.
