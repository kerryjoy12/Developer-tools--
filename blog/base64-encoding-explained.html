Base64 explained: bytes, UTF-8, and the size trade-off

Base64 makes bytes portable through text-only channels. It does not make them secret.

8 min readNovember 8, 2026

Base64 is a binary-to-text encoding specified in RFC 4648. It translates bytes into characters from a restricted 64-symbol alphabet, plus optional padding. This is useful when a protocol, document format, or transport is designed to carry text but an application needs to include arbitrary bytes. The encoding is deterministic and reversible, which is exactly why it should not be confused with encryption: a reader needs no key to decode a value.

From bytes to six-bit indexes

Each Base64 character represents one of 64 values, so it carries six bits of information. The encoder takes three input bytes—24 bits—splits them into four 6-bit groups, and uses each group as an index in the alphabet. The standard alphabet consists of A–Z, a–z, 0–9, plus, and slash. Three bytes therefore become four printable characters. This ratio explains the familiar expansion of about 33 percent, not counting padding or a data-URI prefix.

bytes:       01001000 01101001
groups:      010010 000110 1001.. ........
Base64:      S      G      k      =
text:        "Hi" → "SGk="

The example has two bytes, not three. The encoder fills the unused low-order bits with zeroes and uses an equals sign to indicate that the final output group represents fewer source bytes. One source byte typically needs two Base64 symbols followed by two padding symbols; two source bytes need three symbols and one pad; a multiple of three needs no padding. Padding preserves enough information to reconstruct the byte count unambiguously.

Text starts with a character encoding

Base64 itself does not know about letters, emoji, or languages. It encodes bytes. To convert text, an application first serializes characters to bytes using an agreed encoding—UTF-8 is the common choice for the web—and then Base64-encodes those bytes. Decoding must reverse the operations in the correct order. For example, the UTF-8 representation of a non-ASCII character uses multiple bytes. Passing that character directly to legacy btoa, which expects a string whose code units fit in a single byte, can throw an error or produce the wrong bytes.

Modern browser code can use TextEncoder to obtain UTF-8 bytes and TextDecoder to reconstruct text. A Unicode-safe round trip is therefore: string → UTF-8 byte sequence → Base64 characters → byte sequence → UTF-8 string. If the decoded bytes are not valid UTF-8—because they represent an image, archive, or arbitrary binary—the result should remain bytes; displaying them as text is not a faithful file reconstruction. Use binary-aware APIs when you need to preserve an actual file.

URL-safe Base64 is a variant, not a new secret format

The standard plus and slash characters have special meanings in some URL contexts, and a trailing equals sign can be awkward in file names or query strings. The URL-safe alphabet replaces plus with hyphen and slash with underscore. Some specifications also omit padding because the output length or enclosing format is enough to reconstruct it. These choices must match the consumer: do not normalize or remove padding unless the receiving protocol permits it. URL-safe Base64 is still the same reversible encoding and offers no confidentiality.

Base64 is not interchangeable with percent-encoding. Percent-encoding represents reserved bytes using hexadecimal escapes within a URL component; Base64 converts arbitrary bytes into a different alphabet. A URL may contain a Base64 token, and that token may itself need URL-safe treatment, but the layers solve different problems. Document each layer in a protocol so both producer and consumer know where encoding begins and ends.

Data URIs: useful for small embedded resources

A data URI can embed content inline using a scheme, media type, optional parameters, a Base64 marker, and encoded data. For instance, an image data URI can be used as an image source without a separate image request. This is handy for a tiny icon, a self-contained prototype, or a fixture that should travel with a document. The file-to-data-URI workflow in the Base64 tool reads the selected file through the browser File API; the file contents are not sent to a conversion server.

Inline encoding has costs. It enlarges the HTML or CSS, makes cache reuse less granular, can complicate content-security policies, and may make source diffs noisy. A browser can cache an external image independently, while a data URI is repeated wherever it appears. Large embedded payloads also make markup harder to inspect and maintain. Measure a real page rather than assuming fewer requests always means better performance; HTTP multiplexing and cache behavior matter.

Security: never mistake obscurity for protection

Base64 can make a binary value printable, but anyone can reverse it. It is not encryption, hashing, a digital signature, compression, or access control. Putting an API key in Base64 does not protect it from a person who can read the URL, source, log, or request. Likewise, encoding a password in an HTML data attribute does not make it safe. Use an authenticated encrypted channel for transit, a managed secret store for credentials, and established cryptographic protocols for confidentiality and integrity.

Encoded strings can still contain sensitive data. They are often longer and may be copied into terminal history, logs, analytics, browser history, or tickets. Treat a Base64 value with the sensitivity of the bytes it represents. A checksum can detect accidental changes when computed and compared through a trusted process, but Base64 alone does not detect tampering. For a security-sensitive message, select a reviewed authenticated encryption or message-signing scheme instead of inventing one around an encoding.

When encoding fails

  • Check for whitespace introduced by email, line wrapping, or copy-and-paste. Some decoders permit it; not all consumers do.
  • Confirm that the input uses the expected alphabet, especially if a value contains - or _.
  • Inspect the number of characters and whether the receiver accepts omitted padding.
  • Decide whether you are decoding text or bytes. Replacement glyphs can signal binary data or an incorrect character encoding.
  • Check whether a data-URI header such as data:image/png;base64, should be retained or removed before a decoder consumes the payload.

Use the client-side Base64 Encoder & Decoder to experiment with Unicode, URL-safe output, and a local file. For the common security misconception, read Is Base64 encryption?. For exact interoperability, check the RFC and the consuming API’s documentation—an encoding can be valid in isolation but still be rejected by an application that expects a different wrapper or alphabet.

Remember

Encoding changes representation, not secrecy. Keep decoded bytes, character encoding, and transport rules explicit.
