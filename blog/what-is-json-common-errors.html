JSON: syntax, structure, and the errors that trip people up

JSON is deliberately small. Knowing its strict rules makes parser messages much less mysterious.

DevTools Hub Editorial Team8 min readNovember 8, 2026

JavaScript Object Notation (JSON) is a text format for representing data. Despite the word “JavaScript” in its name, JSON is language-independent and defined by a concise grammar standardized in RFC 8259 and ECMA-404. It is popular because people can read it, parsers are available in almost every programming language, and its values map naturally to common data structures. Its small grammar is also intentionally strict: the syntax accepted in a JavaScript object literal is not always valid JSON.

Six kinds of JSON values

A JSON value can be an object, array, string, number, boolean, or null. Objects associate quoted string keys with values; arrays hold ordered values. Objects and arrays can be nested to form trees. At the top level, a document may be any one JSON value—not only an object—although some APIs impose a narrower contract.

{
  "service": "catalog",
  "healthy": true,
  "attempts": 3,
  "owner": null,
  "regions": ["eu-west", "us-east"]
}

JSON does not define comments, functions, undefined values, symbols, dates, or references between nodes. A date is commonly serialized as a string, and a consumer must agree on its format and timezone semantics. A value that looks like a number may also need to be a string if exact decimal precision or leading zeroes matter.

Common syntax errors and how to locate them

Single quotes and unquoted keys

JSON strings and object keys use double quotation marks. {'name': 'Ada'} is a JavaScript-style object literal, not JSON. Write {"name": "Ada"}. A parser reports the first place the grammar becomes impossible, which can be a character after the actual mistake—for example, it may complain at the key’s first letter because it expected a double quote before it.

Trailing commas and missing separators

Every object member except the last is followed by a comma, and commas are not permitted after the final member or array element. Missing commas between entries produce a similar error. A useful debugging tactic is to inspect the line before the reported position, especially after editing or generating a nested structure. When you delete an item, remove exactly one adjacent comma rather than blindly adding punctuation until the parser accepts the document.

Invalid numbers

JSON numbers follow a constrained decimal grammar. Leading zeroes are not allowed except for the value zero itself; a plus sign cannot prefix a number; and NaN and Infinity are not valid JSON values. Scientific notation such as 1.25e3 is valid. JavaScript parsers use IEEE-754 numbers, so large integers beyond the safe integer range may lose precision when parsed. If an identifier or exact large integer must round-trip, represent it as a string or use a parser with an explicit arbitrary-precision strategy.

Escapes, control characters, and Unicode

A JSON string cannot contain an unescaped line break or raw control character. Use escapes such as \\n, \\t, and \\u00E9. A backslash must itself be escaped when included literally. Unicode is allowed in strings, but the way a particular application normalizes equivalent sequences can matter when comparing or signing text. JSON syntax does not promise that two visually identical strings use identical code points.

Syntax validation is not schema validation

A parser answers one narrow question: “Can this string be read as a JSON value?” It cannot decide whether a field is required, whether an email address is meaningful, whether a number is within a business limit, or whether the user is authorized to perform an operation. Those are contract, domain, and security checks. A document such as {"quantity": "many"} is valid JSON even if an endpoint expects a positive integer.

Production services should validate data in layers: parse it; validate its structure against an API contract or schema; apply domain invariants; and perform authorization checks independently. A client-side schema check improves feedback but never replaces server-side validation because clients can be modified. Keep input shape and semantic validation separate in tests so an error points to the right layer.

Formatting, minification, and deterministic diffs

Formatting changes whitespace between tokens without intending to change the value. Indentation makes nesting visible and code review easier. Minification removes insignificant whitespace, which can reduce a text payload. Neither operation makes JSON “more valid” than the parser’s validation result. Sorting object keys may make diffs predictable, but it can also obscure intentional ordering in systems that incorrectly rely on it; arrays remain ordered and must not be sorted casually.

JSON object member order is not a suitable semantic contract. Many parsers preserve the order they encountered, but applications should not depend on that behavior unless the protocol explicitly requires it. If you need canonical bytes for hashing or digital signatures, use a defined canonicalization scheme rather than an arbitrary pretty-printer, since whitespace, key ordering, Unicode handling, and number formatting all affect bytes.

A repeatable debugging workflow

  1. Capture the exact response body, not a copied visual rendering that might omit escaped characters.
  2. Check the HTTP status and content type; a proxy error page is not JSON merely because the endpoint is an API.
  3. Use a parser or formatter to find the first syntax error. Read a few characters before and after the position.
  4. Check quotes, commas, escape sequences, and number spelling; inspect the preceding line for missing punctuation.
  5. Once parsing succeeds, validate the schema and then the application’s rules separately.
  6. Reduce the failure to the smallest valid or invalid example and add a regression test.

Quick rule

Use a JSON parser for grammar, a schema validator for shape, and application logic for meaning. One check cannot stand in for all three.
